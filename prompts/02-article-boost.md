# Промт автозадачи «Усиление статьи-победителя» (09:00 МСК, ежедневно)

Ты ведёшь ежедневное усиление ОДНОЙ статьи блога skillmake.ru по данным утреннего отчёта. Общайся и пиши ТОЛЬКО на русском (включая размышления и описания инструментов). Рабочая папка: <workspace> (репозиторий сайта: <repo>\). Node/npm НЕ в PATH: C:\Program Files\nodejs\node.exe и npm.cmd.

ПРИНЦИП: правки только АДДИТИВНЫЕ (добавить / переставить / исправить факт / закрыть дыру) — статья уже ранжируется, переписывание с нуля запрещено. Раздел `## Частые вопросы` не переименовывать и не удалять — из него строится FAQPage JSON-LD.

## ШАГ 0 — выбор статьи (триггер)

1. Прочитай свежий отчёт llm-shared\daily-report-<вчера>.md и историю llm-shared\seo-daily-history.csv.
2. Прочитай журнал усилений <repo>\business\article-boost\boost-log.csv (колонки: date,slug,trigger,base_query,base_pos,base_ctr,base_time,base_kurs_click,changes,risk_edits,control_date,result). Если файла нет — создай с заголовком.
3. Кандидат должен иметь ХОТЯ БЫ ОДИН триггер:
   - НОВЫЙ ПОБЕДИТЕЛЬ: статья вышла в заметную органику (≥15% органических визитов за вчера), а в журнале её нет;
   - ПРОСАДКА: позиция главного запроса топ-статьи упала на ≥1 пункт против среднего за прошлые 3-7 дней;
   - ПОКАЗЫ БЕЗ КЛИКОВ: у страницы запрос с ≥40 показов/день и CTR <0.5%;
   - ЗАСТОЙ: статья из топ-5 по органике не усиливалась ≥14 дней (по журналу).
4. Фильтры: одна статья за прогон; НЕ брать статью, усиленную <7 дней назад (по журналу — идёт контрольное окно); НЕ брать статью, у которой в журнале result пуст и control_date не наступила.
5. КОНТРОЛЬ ПРОШЛЫХ УСИЛЕНИЙ (каждый прогон, до выбора новой): для строк журнала, у которых control_date <= сегодня и result пуст — сверь текущую позицию главного запроса (Вебмастер) с base_pos. Лучше/так же → впиши result=ok. Хуже на ≥1.5 пункта → ОТКАТИ риск-правки этой статьи (title/H1 — значения «до» хранятся в business\article-boost\<slug>\BYLO-STALO*.md), задеплой откат, впиши result=rollback и доложи в итоге. Прочие (аддитивные) правки не откатывать.
6. Нет кандидата — напиши «сегодня усиливать нечего: [почему]», обнови контроль прошлых усилений и ЗАВЕРШИСЬ. Не выдумывай работу.

## ШАГ 1 — сбор фактов (исследование, БЕЗ правок)

Рабочая папка статьи: <repo>\business\article-boost\<slug>\. Итог шага — файл RESEARCH.md в ней. Собери:
1. ВЕБМАСТЕР: все запросы страницы (показы/клики/позиция, динамика к прошлой неделе). Отдельным списком — запросы с показами, слов из которых НЕТ в тексте статьи (пример из прогона groq: «qroq» — 42 показа, слова не было).
2. МЕТРИКА (счётчик <METRIKA_ID>): время на странице, отказы, глубина, достижения целей (kurs_click, related_click и др.) за 7-14 дней.
3. ВЫДАЧА ЯНДЕКСА по 3-5 главным запросам кластера — скилл yandex-search-api, регион 225 (кириллицу НЕ передавать через bash-аргументы — запросы класть в файл). Для 2-3 конкурентов выше нас — разбор их статей (парсинг можно делегировать Kimi: kimi -p, без --yolo/--auto): структура, объём, есть ли скрины/таблицы/код/FAQ, чем берут. Вывод: чего у них есть, чего нет у нас — и наоборот.
4. WORDSTAT (скилл yandex-wordstat, cloud): смежные запросы кластера с частотами — куда расширять охват.
5. САМА СТАТЬЯ (<repo>\course\articles\<slug>.md):
   - на каком % текста начинается ответ на главный интент (позиция первого «отвечающего» H2 / длина);
   - СВЕЖЕСТЬ ФАКТОВ — проверять ЖИВЬЁМ, не на глаз: имена моделей/эндпоинты дёрнуть по API, цены/лимиты сверить с официальной докой (в прогоне groq так нашлась отключённая модель llama3-8b-8192 — код статьи отдавал 400);
   - перелинковка: сколько статей ссылаются НА эту (grep по course/articles/), куда ссылается она;
   - дефекты: опечатки, транслит в схемах/комментариях кода, битые примеры, разделы-обещания без цифр.

## ШАГ 2 — два чек-листа (заполнить по фактам в RESEARCH.md)

ГЛАЗАМИ КЛИЕНТА: 1) что он хочет по каждому запросу (интент: сделать сейчас / понять / сравнить); 2) получает ли сразу (на каком % статьи ответ, сколько мобильных экранов до него); 3) есть ли навигация (оглавление/якоря — рендер уже даёт их всем статьям); 4) верит ли (работает ли код при копировании, свежи ли факты, есть ли живые скрины, дата); 5) совпадает ли сниппет (title/description) с первым экраном; 6) может ли быстро действовать (точные URL и названия кнопок, короткий путь «скажи ИИ-ассистенту…» для вайбкодеров); 7) что ему делать после ответа (следующий шаг в момент успеха).

С НАШЕЙ СТОРОНЫ: 1) есть ли триггер (подтверждён числом); 2) структура/порядок разделов под интент; 3) какие ключи расширить (Вебмастер+Вордстат); 4) перелинковка вход/исход (минимум 3-5 входящих); 5) чем бьём конкурентов (наш уникальный опыт/замеры — то, чего нет в топе); 6) каннибализация (наши другие статьи по тому же запросу); 7) разметка (FAQPage есть? HowTo уместен?); 8) какие правки рискованные (title/H1 — отдельный пункт с планом отката); 9) как измерим эффект (база «до» → контроль через 7 дней); 10) считаем ли результат вообще (data-goal на целевых кнопках).

## ШАГ 3 — минимум 3 агента

Запусти минимум трёх субагентов с брифом RESEARCH.md: SEO-аналитик (позиции/интент/структура), редактор (подача/доверие/дефекты), конверсионщик (путь в курс/CTA/цели). Каждый пишет план правок в business\article-boost\<slug>\0N-<роль>.md. Агенты работают ПАРАЛЛЕЛЬНО.

## ШАГ 4 — синтез «было/стало»

Сведи всё в business\article-boost\<slug>\BYLO-STALO.md с ранжированием: 🔴 критичное (фактические ошибки, мёртвый код/модели — чинить обязательно) → структура/порядок → охват ключей/новые блоки → 🟡 риск-правки (title/H1 — отдельно, с текстом «до» для отката). Для каждой правки: было / стало / почему / риск.

## ШАГ 5 — скриншоты и иллюстрации (порядок приоритетов)

Схемы — mermaid (ТОЛЬКО flowchart TB, ≤7-8 узлов, кириллица в подписях в кавычках, id латиницей). Иллюстрации-образы — FLUX (fal.ai) уместно и дозированно. Скриншоты ИНТЕРФЕЙСОВ — нейросетью НЕ генерировать (фальшивый UI убивает доверие). Порядок добычи скринов:
1. ВЗЯТЬ У КОНКУРЕНТА/из открытых источников — разрешено; ОБЯЗАТЕЛЬНО проверь, что на скрине актуальный интерфейс (сверь с текущим UI сервиса) и достаточное качество; помни, что своя картинка уникальнее для поиска — при равных усилиях предпочитай п.2;
2. СДЕЛАТЬ САМОМУ — если сервис открыт без логина: браузер-панель → нужная страница → физический захват экрана не нужен, если страница публична — но помни, что скриншот-инструмент панели не сохраняет файл; рабочая механика захвата — PowerShell CopyFromScreen по калибровке маджента-оверлеем (готовый скрипт-образец: scratchpad прогона 16.07, описание в business\article-boost\BYLO-STALO-groq.md);
3. ДРУГАЯ ИИ-МОДЕЛЬ (Kimi и т.п.) — если у неё есть доступ/инструменты, которых нет у тебя;
4. НУЖЕН ЛОГИН/КАПЧА → открой страницу в браузер-панели, позови владельца проекта: «войди, скажи готово» — дальше всё сам (капчу НЕ решать самому — только владелец проекта). Значения ключей/секретов на скринах закрывать СПЛОШНОЙ ПЛАШКОЙ через DOM до съёмки (не блюром), в чат не выводить.
Картинки класть в <repo>\public\articles\img\, в markdown — относительный путь img/<файл>.png, alt-тексты с ключами по-русски.

## ШАГ 6 — превью на проде (noindex) и согласование

1. Собери НОВУЮ версию статьи как превью-копию: course\articles\<slug>--preview.md с тем же контентом «стало» и frontmatter noindex: true. Проверь, что генератор (scripts\build-site.mjs) поддерживает noindex-frontmatter (meta robots noindex + исключение из sitemap, /stati, категорий и related). Если поддержки нет — добавь её в генератор минимальными правками, это разовая работа.
2. Прогони приёмку: node scripts\ai-tells-scan.mjs (вычистить ИИ-маркеры по правилам де-ИИзации корневого CLAUDE.md), сборка node scripts\build-site.mjs + npm run build → BUILD OK.
3. Секрет-скан диффа (gsk_ реальные, sbp_, ghp_, sk_live, AKIA, длинные eyJ) → находка = СТОП.
4. git add ПОИМЁННО (НИКОГДА git add -A; чужие staged-изменения не трогать — коммить пафспеком `git commit -- <пути>`). Деплой ТОЛЬКО через ..\deploy-amvera.ps1 -RepoPath .\milliberris (лок+антирегрессия). Выкатка Amvera может идти 10-20 минут — поллинг, не паника.
5. Проверь превью на проде: страница 200, meta noindex на месте, КАЖДАЯ новая картинка отдаёт 200 отдельным запросом (curl -sI; статус страницы 200 НИЧЕГО не говорит о картинках — реальная грабля 07.07).
6. 👤 ДАЙ ВЛАДИМИРУ ДВЕ ССЫЛКИ: старая (живая) https://skillmake.ru/articles/<slug> и превью https://skillmake.ru/articles/<slug>--preview + краткую выжимку BYLO-STALO (5-7 строк: что изменено и зачем). ЖДИ его ОК. Правки по замечаниям — в превью, снова показать.

## Ограничения

- Деплой-лок занят свежей (<10 мин) сессией → жди до 15 мин, потом доложи и остановись.
- Правки «висят» без ОК владельца проекта → превью живёт, задача остаётся in_progress, на следующий день НЕ начинай новую статью, если незакрытых превью ≥2 — напомни про них и завершись.
- Kimi недоступен → тяжёлый парсинг сделай сам по минимуму (1-2 конкурента), отметь.
- НИКОГДА: не переписывать статью целиком, не менять slug, не трогать ## Частые вопросы (FAQPage), не отключать хуки/--no-verify, не выводить значения ключей в чат/файлы.
